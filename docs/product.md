# 上架评审会签台：把多 Agent 协作做成能拍板的定价评审

## 这是什么

当前产品是 **商品上架评审会签台**，不是昨天的「小店经营」回合向导，也不是更早的 8 回合虚拟沙盘。

老板把商品链接或分享文案，连同采购价、包材、快递、目标毛利和周转金一起交给系统。七个角色按职责会签：研究员提取证据与待确认项，成本会计核算单件成本与保本价，市场分析师给出稳价 / 跟价 / 冲量三套策略并做 30 天现金流推演，风控独立复核，必要时做最多两轮定向经济修正，文案师起草可兑现标题和卖点，最后停在掌柜拍板门。拍板通过或驳回都会封存一条可回放的事件链。

界面的主视觉是「会签台账」，不是四个通用 KPI 卡片，也不是把 seq、hash、调度分放在第一屏当主角。那些凭证可以在侧栏事件流和每节下方的凭证行里核对。

## 为什么要这样改

上一版控制台往往「一下就跑完」，用户只能看到一份已经封存的结果，看不出谁向谁交了什么、风控卡住了哪一项、修正前后数字怎么变。现在要让协作过程本身可见、可核对、可拍板：

- 实时事件流：评审通过 `POST /api/agentops/runs/stream` 边算边推事件，不靠前端 `setTimeout` 假装耗时。
- 职责交接：会计不算整套方案，市场消费保本价后出三套策略，风控用领域检查项独立复核，文案在会签之后再写。
- 定向 Self-Loop：只有推广占比、活动破保本、策略毛利/备货这类经济问题才会重跑；证据不足或周转金硬约束不会靠盲目砍广告空转。每一轮记下修正前后的售价、毛利、p10、推广预算、活动折扣、未通过项和推荐策略。
- 掌柜拍板：控制台默认「需我拍板」（`autoApprove: false`），在待拍板状态选择策略后「通过」或「驳回」。裸调 API 未传该字段时仍默认自动放行，保持兼容。历史卷宗可以「回放已封存事件」，并标明这不是实时工作。
- 规则与模型诚实标注：调度、核算、风控默认是本地确定性规则 Harness；外部模型只用于文案节点，不通过校验就显式记为「模型回退」，绝不把规则结果说成模型推理。

## 保留了什么是真的

- 多角色分工：成本会计 / 市场分析师 / 风控审计 / 文案师各有职责，不是同一个模型换个名字。
- 交叉验证：定价要过风控的既有检查（保本、毛利、推广占比、退货、竞品带、备货/断货、活动折后价等）；修正过程在「修正前后对比」里逐项看得见。
- 可核对：每一步有哈希，方案有指纹。同样的输入永远算出同一份方案。
- 锁定与留痕：拍板通过或驳回后事件链封存；改价必须重新评审，不能偷偷改已封存结果。
- 定价公式本身没有改。`src/engine`、沙盘 `simshop` 和既有定价计算仍作为回归基准保留，只是不再作为当前产品界面。

## 扔掉了或降下权重的东西

- 以「开始核算 / 看三套方案 / 去复制上架」为主线的掌柜向导（已从 `App.tsx` 卸下，组件仍可复用）。
- 剧本（spring / supplycut / pricewar）和随机种子驱动的「剧情」。
- 虚构茶饮零食品类、虚构供应商断供，作为当前产品叙事。
- 把节点图、调度分、事件哈希当作第一屏主视觉。

## 数字是怎么来的

这些公式与改版前一致，界面和文档都不另编一套算法。

| 量 | 公式 | 为什么要这么算 |
| --- | --- | --- |
| 退货摊销 | 退货率 ×（来回运费 + 包材 + 商品折损） | 退货的钱不是「概率」，是实打实要出的两趟运费 |
| 保本价 | 一件成本 ÷（1 − 佣金率 − 支付费率） | 平台是按成交额抽成的，所以除数要减掉抽成 |
| 推广摊销 | 日预算 ÷ 当日总单量 | 单量越高，每单背的推广费越薄，这就是冲量价能成立的前提 |
| 需求 | 市场日单量 ×（竞品价 ÷ 售价）^ 弹性 + 推广单量 | 用老板自己填的竞品价和该价位的日单量做锚点，不凭空造流量 |
| 备货上限 | 周转金 ÷（采购价 + 包材） | 账期没到，钱压在平台里，卖得多反而可能断货 |
| 推荐口径 | 在毛利率达标且不为负的方案里，取 30 天 p10 最高 | 不赌最好的那天 |

一件成本 = 采购价 + 包材 + 快递 + 平台佣金 + 支付手续费 + 退货摊销。30 天推演每天需求按 ±28% 波动，备货受周转金限制，回款按平台账期延后，跑 200 次取 p10 / p50 / p90。

## 三条硬规矩

1. **不编数据。** 没有抓取平台、没有假装有实时热销榜。市场日单量、竞品价、费率全部由用户填；短链或缺失字段会作为待确认问题留给掌柜，不会伪装成已抓取事实。
2. **不编承诺。** 卖点只从用户勾选的服务承诺和算出来的真实差价里生成；模板句标「需你确认」。
3. **不藏着算式，也不假装很慢。** 成本拆解、检查项、修正前后对比和推荐理由都可以在会签台账里看见；协作可见性靠真实交接与定向修正，不靠前端空等。

## 下一步能做的

- 多规格 SKU：一个链接下多个规格，分别算价。
- 竞品价带：填 3–5 个竞品价，自动找出价格带里的空档。
- 历史对比：同一件商品改价前后，方案指纹和利润区间的差异。
- 流式快照：目前实时流推的是事件（标题、说明、哈希），台账里的完整产物在 `done` 到达后填齐；若要把会签各节随节点完成逐步填满，需要在事件流里附带快照。
- 平台后台对接：目前是复制粘贴 + CSV，再往下需要各平台开放接口或浏览器插件。

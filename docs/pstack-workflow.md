# pstack 项目执行约定

## 入口与范围

以当前用户任务为范围，先读 `AGENTS.md`、`README.md`、`package.json` 和受影响代码，检查 `git status --short`。保留用户已有改动。`docs/design.md`、`docs/plan.md`、`docs/unit-notes/` 提供设计和历史证据；勾选状态必须与当前代码核实。

优先从当前环境已安装的 pstack 插件或技能目录发现 `skills/poteto-mode/playbooks/`，读取对应任务 playbook；不依赖特定用户目录或缓存哈希。未找到时报告缺失，使用本文的项目约定继续工作，不声称已运行插件。不要复制整个插件到仓库。

## 按任务选择流程

| 类型 | 首要动作 | 完成证据 |
| --- | --- | --- |
| feature | 明确用户行为、数据模型和验收标准 | 新行为的测试及实际运行证据 |
| bug-fix | 复现问题并定位根因 | 修复前失败、修复后通过的复现或回归证据 |
| refactoring | 明确行为不变的边界和调用方 | 相关调用方及现有行为验证 |
| perf-issue | 固定负载、环境、指标和基线 | 相同条件下的前后测量 |

## 每个可验证单元

1. 写明目标、受影响路径、验收条件和证据位置。小任务可直接在会话中记录，较大任务另建任务记录，避免覆盖历史计划。
2. 规划四项吞吐检查：阻塞前置条件、独立工作流、共享可变状态、最小安全拆分。无适用项也保留并写 `n/a: 原因`。共享文件写入按顺序进行。
3. 明确数据模型后再实现。支持子代理时，将边界明确的实现委派给单一负责人，由主代理审查差异；独立路径才并行。环境不支持时记录限制，分阶段自行完成。模型继承当前会话，不强制使用插件示例中不可用的型号。
4. 审查行为、边界、调用方、错误路径和范围外改动。修复审查问题后验证，再开始下一单元。
5. 记录命令、结果、证据路径及限制；完成报告说明改了什么、为何这样选择、验证结果、四项吞吐检查及未决事项。

## 验证矩阵

| 维度 | 项目命令或证据 | 适用规则 |
| --- | --- | --- |
| 静态检查 | `pnpm lint`、`pnpm typecheck` | 代码变更运行相关检查 |
| unit | `pnpm test` 或有针对性的 Vitest 用例 | 验证行为和回归；文档修改可记 n/a |
| live | `pnpm e2e`；需要时使用 `pnpm dev` 手动检查实际页面或 API | Playwright 配置自动启动隔离测试服务，不读取用户模型配置或改动历史卷宗；同端口开发服务需先关闭；页面/API 改动必须验证对应表面 |
| perf | 固定输入下的耗时、吞吐或资源用量对照 | 性能任务或影响关键路径时测量；其余说明 n/a 原因 |

运行环境使用 Node.js 22 或更高版本及 pnpm 10。首次安装依赖执行 `pnpm install`。`pnpm exp` 仍是未实现占位入口，不能作为验证通过的证据。

测试通过不能替代实际运行验证。失败、未运行或结论不明要明确记录；不得将这些状态写成 pass。纯文档任务核对链接、路径、命令与差异即可，不额外制造应用测试。

## 收尾

检查 `git diff --check` 与最终差异，给出变更文件和验证摘要。不自动提交、推送、创建 PR、合并或部署；这些动作须有用户授权。用户暂停时保留当前改动，记录已完成部分和下一步。
